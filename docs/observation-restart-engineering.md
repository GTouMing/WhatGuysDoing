# 授权跨重启失效与安全收束候选

**当前状态：原观察凭证恢复的历史推演，不再是公开观察启动协议。** [R19-Q162／ADR-0011](<adr/0011-public-read-only-observation.md>) 已取消授权文件、旧凭证失效／重签和秘密领取职责；下文 Q153/Q158 相关首故障留痕及可靠保存门退出公开实施路径，不等于这些机制得到证明。R20-Q163–Q165 已确认：enabled 且必要条件就绪时正常服务器启动自动开放、正常重启再次公开，替代 Q154 每次人工开通；内置端口允许显式对外绑定、不强制回环、无观察认证，远程 WebGPU 仍须同源 HTTPS/WSS 并禁止第三方嵌入；活动页等份轮转，另设一个有限普通公开 HTTP 桶，共用总预算，同页多连接不加份额，全站最多 8 个活动页、满拒新且不踢合格旧页，不作账号／IP／指纹自然人识别，同一人可多页、不扩预算。R21-Q166–Q169 已确认：真故障只停观察、游戏继续；故障消除、相关旧输出／写入已收束且重新就绪后才有限自动重建当前，未知或耗尽保持关闭并提示管理员，不无限重试／补历史，整站次数／时限／资源待工程核定、不套页重连／压力值。单纯超过 5 秒墙钟回拨只告警，新鲜度／等待／重试／保留／峰值沿单调时钟不延寿，真实一致性故障另处理。运营者反向代理负责 HTTPS/WSS 和证书，模组不内置证书管理，代理产品／配置未选；同源／禁止第三方嵌入／无观察认证及 Q164 显式外绑不变。服务开停／故障／概览代次管理仅走控制台和受控配置，无网页／游戏内管理或授权者名单；旧输出／缓存任务的实际退出、晚到副作用、代次和成本不能因取消认证而消失。现行迁移见[公开访问合同](<observation-public-access.md>)；下文 Q154 历史选择及其推演原样保留，不再是现行门槛。V1A/V1B 保持停止，V2 卡、产品实施及生产开通未批准，不授权构建／运行／测试／监听／游戏／环境修复或删除历史数据；K、完整容量及双加载器事实仍未验证。

## 一、已选行为与新增决定分开

| 已选依据 | 必须保持的边界 |
| --- | --- |
| [Q38–Q41](<observation-design.md#L85-L88>) | 授权、凭证有效性及撤销跨重启保留，登录不保留；轮换不能恢复旧凭证，期限不自动延长 |
| [Q65–Q67](<observation-design.md#L128-L130>) | 单进程串行可靠保存；故障不凭重读成功重开；不能确认最新撤销时恢复出的全部旧凭证失效；管理成功同时需要可靠保存与阻断完成 |
| [Q81/Q84](<observation-design.md#L149-L152>)、[Q119](<observation-design.md#L295>) | 缺文件不自动初始化；超过 5 秒回退使全部旧凭证失效并显式恢复；较小回退也不能复活已判定过期的许可 |
| [Q117/Q118](<observation-design.md#L293-L294>) | 原文至多 120 秒；正常等待不是失败，终结但未确认则可靠失效；重启不能找回原文或假设内存确认已经保存 |
| [Q136/Q137](<observation-design.md#L319-L320>)、[Q146](<observation-design.md#L342>) | 文件与任务仍有界；真实必要安全更新无法承接即全站关闭观察并报告未完成，游戏继续 |

Q66 的条件是**实际不能确认最新撤销结果**，没有规定“进程非正常退出一律全员重签”。粗粒度运行标记会扩大无法确认的范围；用户已在 Q153 接受“缺少可信安全收束即统一显式恢复并失效全部旧凭证”的代价。这是对恢复分类的新增决定，不倒写为 Q66 原已规定；可信收束且无其他故障仍按 Q41 保留有效凭证。

## 二、只看当前授权文件不能区分的两条路径

假设磁盘上最后可靠文件为同一份状态 S，包含仍有效的凭证 A：

- 路径甲：没有管理变更，观察处于空闲，进程中断；磁盘仍为 S。
- 路径乙：已校验撤销 A，已在内存中封锁认证和发送，但新状态尚未可靠保存便中断；磁盘也仍为 S。

仅检查 S 的 JSON、摘要、版本或当前墙钟，无法区分这两条路径。这是所列模型下的静态反例，不是实际复现，也不是证明所有更细机制都不可能。周期性保存、只在安全事件之后写标记、把排障日志当真源，都不能直接覆盖上述窗口。

候选在允许产生这种窗口之前可靠记下“本运行尚未收束”，使甲乙重启后都不直接采用 S 开放观察。代价是它不能仅凭该标记判断甲是否无害。

## 三、候选状态机：运行是否收束，不等于是否获准恢复

此处“可信安全收束”仅是工程条件的简称：相关入口已封锁，已受理安全更新与交付终态可靠完成，旧任务不再具有修改授权或发送世界数据的能力，必要时间边界已保存。不是退出码、停止日志、队列为空或调用 close；也不新建领域术语。

文件元数据至少须分别表达**运行是否仍有未收束工作**与**是否仍要求显式恢复**。字段名称、编码、序号推进和完整组合校验尚未选定；它们仍在原有 16 KiB 元数据候选包络内核算，不新建无界日志或额外授权真源。清理工作完成不能自动清除恢复要求。Q154 的本次开通意愿另须核定，不把它保存成跨运行的自动开通许可。

| 阶段/读到的依据 | 观察与管理入口 | 候选下一步及限制 |
| --- | --- | --- |
| 新进程开始 | 默认拒绝世界认证/发送，本次开通意愿不沿用；不恢复旧登录、预览或原文 | 核对文件来源、格式、独占与部署条件；缺失/不可信走既有初始化或显式恢复，不能默认空授权；Q154 的本次控制台明确开通不可省，也不能替代这些条件 |
| 上次可信收束、无恢复要求，其他前提满足 | 尚不开世界入口，不生成秘密 | 在串行可信基线上先可靠保存本运行“未收束”；仅调用保存或只写临时文件不算完成 |
| 本运行开始已可靠记录 | 仍须完成 Q154 本次明确开通、安全时间/资格检查及其他开通门 | 可能产生持久失效义务的时间判定、授权更新及交付须受该先行边界保护，随后才可能开放；首次读写失败门仍未闭合，见第五节 |
| 运行中撤销、到期、交付失败或故障 | 立即采用既有阻断边界；故障需要时全站关闭 | 相关存储/授权故障使本次开通意愿失效；同一有界所有者串行保存终态，运行保持未收束；内存收敛不等于跨重启完成 |
| 准备正常结束 | 先封锁新增许可、管理变更和应用层世界发送 | 关闭或隔离全部会产生安全更新/交付确认/旧文件写回的入口与任务；等待已有所有者完成必要终态，不能仅清队列 |
| 必要终态与时间边界已可靠完成 | 不再接受本运行的新工作 | 最后一次串行提交“已收束”，保留尚未解除的恢复要求；提交之后不能再有旧授权写回或旧世界发送。若要再次启用，必须重新经过先行运行标记及 Q154 本次控制台明确开通 |
| 读到未收束，或任一收束证据不可信 | 关闭观察，转控制台显式处理 | 按已接受 Q153，缺少可信收束本身即按不能排除遗漏处理，全部旧凭证可靠失效后按需重新签发；保留可核对的授权及授权者，恢复时核对名单 |
| 已收束但仍有恢复要求 | 仍关闭观察 | Q119 等故障不会因为正常停机或失效已写完而自动获准恢复；控制台处理仍不可省 |

这里要求消除的是旧任务的授权变更与世界发送能力，不是假称进程内所有对象已物理释放。真正隔离的缓存/取消残留仍计原内存与峰值账；有关联的持久写者未退出或仍可能写回，就不能据此宣布收束。收束不成不能无限阻塞游戏 tick；具体有界等待、关停协调和 I/O 退出仍须核定，没有新增超时数值或运行许可。

## 四、交付、时间与最后一笔保存

- **交付事务。**候选将新摘要和“等待交付”一起可靠保存后才交付原文；确认必须匹配授权、凭证及本次事务，再由原所有者可靠保存终态。原文已被复制给领取者不证明确认已可靠保存；崩溃后不能从丢失的内存、旧回调或日志补确认。停机终结仍未确认的交付，按 Q118 可靠失效，不恢复旧凭证。具体可信确认通道仍无证明。
- **时间不可倒退覆盖。**本运行已用于权限安全判断的时间边界不能在较小回拨后用较早的“当前时间”覆盖；已判定过期的记录须保持失效。最终保存须包含必要的已观察时间边界和失效结果；只在最后取一次墙钟不足。超过阈值的回拨另保留全站失效及显式恢复要求。仅能跨重启比较可靠保存的边界，不承诺发现全部离线回拨。
- **较弱保存不能宣布收束。**旧保存开始后到来的更强安全目标仍由原所有者承担；旧保存完成不能释放它或清故障。最终整文件提交须基于串行提交时的可信版本，不能让 B 的旧快照覆盖已经保存的 A 撤销，沿用[现有所有权约束](<observation-authorization-engineering.md#L91-L95>)。
- **最后提交不是最后一行代码。**提交“已收束”前必须封住之后可能恢复旧权的发布路径；提交后若还有可受理管理、回调写回或应用缓冲自动 flush，就没有所声称的最终边界。资源的 destroy、线程中断与停止日志均不能替代该证据。

## 五、首次标记前的故障仍是独立缺口

反例：旧文件显示可信收束 → 新启动首次读取/校验或写“未收束”失败 → 进程关闭观察后中断 → 下次存储恢复可读，磁盘仍显示原收束状态。只靠该文件中的标记，无法证明下次仍知道刚才必须显式恢复。

因此本候选**尚未封闭启动协议**。不能把“未服务过”的故障默认为豁免，不把重启当作控制台恢复，也不把一次内存故障标志说成跨重启证据。每次整站启动明确开通已由 Q154 接受，只阻止自动重开；增加独立可信存储/监督者或缩小需记忆的故障范围仍未选择。Q153、Q154 均不关闭首次故障留痕缺口。

同理，文件内运行标识和版本不能识别任意离线整文件回滚；可靠写入、原子替换、目录/设备持久性与单进程所有权仍须另有证据。V1A 的部分存储原语不能证明这些条件。

| 中断点 | 不得采用的推断 | 候选处理/剩余门 |
| --- | --- | --- |
| 首次可靠运行标记之前失败 | 旧文件显示收束，所以可以自动重开 | 保持第五节为阻塞工程门，不能宣布方案闭合 |
| 标记可靠，但尚未服务就中断 | 没有观察者便一定没有安全事件 | 按 Q153，同样进入显式恢复和全部旧凭证失效；这是已接受的保守代价，不是已发生撤销的证明 |

| 新凭证仍等待交付，或确认只在内存 | 凭证到期日尚远/原文已发出，所以交付成功 | 不恢复原文、不补造确认；终结未确认凭证，迟到确认不能复活；缺少可信收束时另按 Q153 全量处置 |

| 大回拨失效已保存，随后正常停止 | 文件已收束，所以故障已获准恢复 | 恢复要求独立保留；不能自动重新授权 |
| 旧写者或关闭缓冲仍能运行 | shutdownNow/空队列意味着所有工作已结束 | 不提交可信收束；有界退出、屏障及实际保留成本仍需证明 |
| 可信收束及全部封锁完成后，进程才异常退出 | 非零退出码必然需要全员重签 | 以可信收束和其他安全条件为准，不以进程退出方式代替；无其他故障时保留仍有效凭证，登录仍丢弃 |

## 七、当前停止代码不能提供这项证据

父代理独立回读了下列片段；结论只覆盖所读路径，不是全仓库缺失证明，更不是运行故障复现：

- [SessionHub.stop:233–254](<../common/src/main/java/github/gtouming/what_guys_doing/core/SessionHub.java#L233-L254>)先置 running=false、关会话并清集合/缓存，之后才停 Web；[tick:257–269](<../common/src/main/java/github/gtouming/what_guys_doing/core/SessionHub.java#L257-L269>)仅在入口检查 running。这里没有看到在途工作的完成屏障；调用 deactivate/lowres.close 的内部保证不由这段证明。
- [WebServer.stop:64–70](<../common/src/main/java/github/gtouming/what_guys_doing/web/WebServer.java#L64-L70>)关闭监听并 shutdownNow，没有等待工作线程结束；已接受连接不等于监听 socket。
- [Session 发送:81–109](<../common/src/main/java/github/gtouming/what_guys_doing/core/Session.java#L81-L109>)在出队后由局部变量继续持有工作；[close:161–168](<../common/src/main/java/github/gtouming/what_guys_doing/core/Session.java#L161-L168>)置关闭、清队列、通知并关闭 WebSocket，没有 join 发送线程。方法返回不证明旧发送/引用全部结束。
- [WebSocket.run:33–52](<../common/src/main/java/github/gtouming/what_guys_doing/web/WebSocketConnection.java#L33-L52>)读消息后调用会话，finally 移除并 close；[close:79–95](<../common/src/main/java/github/gtouming/what_guys_doing/web/WebSocketConnection.java#L79-L95>)取得写锁、写关闭帧并 flush 后关闭 socket。局部写串行化不证明全局入口、读取回调和应用缓冲的安全收束。

没有在这些入口看到本候选的持久收束检查/提交，不把“viewer data service stopped”日志或方法名当成证明。本轮不改停止顺序，也不运行故障注入。

## 八、Q153 的已接受边界与后续门

**用户已回答“接受”：**首版缺少可信安全收束记录时，一律按不能排除未落盘安全事件处理，即使未发现实际撤销/回拨，也关闭观察转控制台显式恢复；使此前全部观察凭证可靠失效，仍需访问者重新签发。保留可核对的授权及授权者记录，恢复时核对授权者名单。可信收束且无其他故障的重启仍保留有效凭证，但不保留登录。

未采用的方向是在缺少可信收束时继续寻找更细的未完成事件证据来保留部分旧凭证；它不能仅凭当前 JSON 合法或“没看到异常”成立，目前也没有经核定的机制。已选统一处置以减少异常路径的信任判断，接受空闲崩溃也可能要求重新领取的代价，不声称具体机制已经安全可用。

Q153、Q154 已确认，当前已提出的问题均有答案。Q154 接受每次整站观察启动增加控制台明确开通的运维代价，不替代故障恢复或可信证据，不选择字段编码、额外存储、完整工程方案或执行许可，也不关闭部署、本机身份、可信交付、限时 I/O、实际内存/任务成本等事实门。两项决定均同步至[ADR-0009](<adr/0009-file-authorization-with-explicit-recovery.md>)；不另增 ADR 或领域术语。

## 九、首次持久写之前：能排除什么，仍不能保证什么

以下是受限模型下的逻辑推演，不是运行试验。父代理回读了第五节反例及 [Q65–Q67](<observation-design.md#L128-L130>)、[Q84](<observation-design.md#L154>)、[Q153](<observation-design.md#L393-L395>)，并核对两份独立静态审查；没有新增源代码或环境能力结论。

### 不可区分的范围

甲从可信收束文件 S 启动；乙从 S 启动，首次读写失败且未留下任何持久痕迹，随后崩溃再启动。若内存已丢失、没有其他可信启动记录，其余可信输入也相同，两次决策看到的仍是 S。仅凭 S 自动放行甲，也会放行乙，不能同时保证这次失败仍要求明确恢复。这只否定所列条件下的区分能力，不证明所有单文件协议都无解，也不证明人工开通是唯一选项。

| 方向 | 实际改变了什么 | 不能据此声称什么 |
| --- | --- | --- |
| 先写一个运行标记，或另加标记文件 | 首次写入成功之后才有持久痕迹 | 若首次操作本身也可无痕失败，仍未覆盖此前窗口；不能仅凭同盘/异盘判断保证，额外文件及失败域尚未选择 |
| 预先消耗一次启动票据 | 把允许启动的证据及消耗顺序另行表达 | 本次消耗前仍可能失败；若上次预消耗后的同一状态仍能自动放行两条历史，反例不变；票据本身不是证明 |
| 从可靠初始化起始终按未收束处理 | 可以直接取消自动采用已收束状态的路径，不只是前移窗口 | 按 Q153 会使每次重启都须恢复并失效旧凭证；这是另一个尚未选择的代价，从现有收束状态迁入的首次保存也未获证明 |
| 增加独立可信启动记录或监督者 | 可能提供 S 之外的区分依据 | 必须核定其自身启动失败、故障域、互斥及可靠保存；不能把缺口推给一个未经证明的外部组件；本轮不选择它 |
| 每次整站观察启动都明确人工开通 | 无论能否认出早期故障，都不会仅凭重启或重读自动开放 | 只解决是否需要人工动作，不证明历史可信、最新撤销完整或全部恢复义务已完成；这是 Q154 已接受的运维门槛 |

### Q154 已接受的行为与仍需证明的前提

- 每次新的进程运行，以及整站观察服务完全停止后的重新启动，默认关闭观察；游戏继续。即使上次可信收束，也须控制台为本次启动明确开通。普通页面断线重连、单页压力恢复和签入不属于整站重新启动。
- 开通意愿不跨运行沿用，不保存成下次自动开放的配置；不得以启动脚本自动重放来代替本次明确动作。本次发生相关存储/授权故障后，先前的开通意愿失效，重读成功也不能自动重新开放。具体命令、绑定和同步方式未选，不声称已证明可以识别人手输入与脚本。
- **本次愿意开通不等于历史可信。**保留旧凭证仍须证实可信收束覆盖此前相关安全事件，以及安全变更、时间判定、秘密生成/交付均受可靠运行标记的前置阻断保护；旧 JSON 合法或管理员点一次确认都不能替代这些前提。
- 收束缺失、不可信或不能排除遗漏安全事件，仍按 Q153 可靠失效全部旧凭证并核对名单；超过阈值的回拨仍按 Q119，小回拨不得复活已过期许可。终结但未确认的交付按 Q118 失效该新凭证，不能把运行中的正常等待直接当全量恢复理由。
- 普通开通不能清除既有恢复要求或补造交付确认；首次无痕故障的恢复义务也不能因改叫“开通”而豁免。需要全量恢复但无法可靠保存时，仍保持观察关闭；不得自动退化为每次重签、要求管理员凭印象担保，或声称故障留痕问题已解决。

用户已接受这项独立运维门槛：无人值守重启后，Minecraft 可运行但观察网站不会自行恢复。这不等于承诺一次人工动作就能安全开放，也不更改可信收束且无其他故障保留有效凭证的政策。首版不采用跨运行自动开通；不能把这一选择说成已证明所有自动启动协议不可能，也不能退回仅凭 S 重读成功自动开放。

### 后续工程门不随政策接受关闭

仍须给出首次失败后的恢复义务如何延续、可信收束如何覆盖最近相关运行、运行标记之前如何封住全部安全事件、故障如何撤销本次开通意愿，以及所有者/任务/发送屏障的具体证明。若这些不能成立，观察仍不开通；本轮不新增运行、存储、内存或任务预算，不重启 V1A/V1B。

## 十、本次开通、故障撤销与迟到完成候选

本节将 [Q154](<observation-design.md#L411>) 落到候选协调边界；只做逻辑推演，不声称已实现或验证。它沿用[有界所有权与整文件基线](<observation-authorization-engineering.md#L79-L95>)和[应用层发送边界](<observation-authorization-engineering.md#L114-L120>)，不新增领域术语、命令、预算或用户决定。

### 三类依据不能互相代替

- **本次明确开通意愿：**仅表达管理员希望本次整站启动开放；不是凭证有效性、故障恢复完成或下一次启动许可。候选将其绑定当前整站运行和本次请求，故障/停止后旧请求不能重新变成当前请求。具体标识、回绕防护和命令绑定仍须核定。
- **当前可信证据：**包括当前串行持久基线、恢复义务、交付终态、安全时间判定及必要运行标记。文件读写成功回调只能报告相应结果，不能自行开放世界入口；结果也不能脱离其对应的运行、请求、所有者和基线使用。
- **实际发送资格：**即使整站已开通，仍要满足当前授权、登录、页范围及发送屏障。整站开关或一次请求版本检查不能代替这些条件，已在应用缓冲中的正文也不属于 OS/代理在途例外。

### 候选协调顺序

1. 控制台本次请求取得有界所有权后记录开通意愿，不先开放任何世界入口。重复请求不能产生无界等待者、回调或新的免费任务；新请求也不能绕过未终结旧写者重新取得持久写权限。具体占用 16 内哪一类名额仍未核定，不能增加第 17 个槽来填缺口。
2. 可信读取、校验、运行标记及必要安全更新沿用唯一串行持久写者，磁盘 I/O 不在游戏 tick 或它会等待的锁内执行。在该运行标记候选中，可靠记下本运行未收束，必须先于会产生持久义务的到期/回拨判定、授权变更及秘密生成/交付；不能先确认过期再补标记。首次读写失败仍走未闭合的第五节缺口。
3. 读取、保存及其他检查完成时，结果先交回当前所有者核对归属与基线，而不是直接设置已开放。证据过时、相关条件已变化或所有权不匹配时不得继续发布；时间经过和回拨也可能使先前检查不足。重取证据或终结失败须沿既有有界路径，不能无限重试或把原意愿改绑到新运行。
4. 最后一次当前检查与开放发布，须和故障/停止撤销使用同一可证明的短同步裁决边界：本次意愿仍有效、证据仍适用、既定恢复义务已完成、没有更强阻断及可能回写旧状态的写者，才允许发布。不得出现“检查通过→故障撤销→旧发布重新开放”。这不是在锁中等待磁盘或网络；具体同步原语与内存可见性尚未选定。
5. 相关故障一经获知即撤销本次资格并发布限制 R，不能等磁盘。故障先于开放裁决时旧结果不得开放；开放先完成时 R 立即拒绝相关新认证和输出生产，全站最多一个 R 前获准≤K的写可返回，然后下一次写前建立匹配 B。已取得正文也不能绕过；一次版本比较不是全入口屏障或实际退出证明。
6. **过期结果不能用于开放，不等于其副作用可以丢弃。**旧写超时、取消或请求换代都不证明物理写终结；其迟到成功/失败仍须归入串行持久状态处理。旧写可能生效或结果不明时，新请求保持关闭，不开始可能与它互相覆盖的提交；取得串行提交所有权后仍须使用当前整文件基线，过时快照重建或拒绝。较弱写完成不得清除较强阻断、复活许可或报告整体成功，未知效果也不得按“回调过期”忽略。

### 六个纸面竞态

| 顺序 | 必须得到的结果 | 尚须实际证明 |
| --- | --- | --- |
| 控制台已表达本次开通意愿，读取尚未返回→相关故障撤销意愿→旧读取成功 | 不开放、不恢复原意愿；重读成功不能自动重开 | 故障可见性及结果归属检查覆盖全部完成入口 |
| 最后检查通过→故障撤销→旧任务准备发布 | 发布失败；不能用分开的检查与赋值让入口复活 | 检查、撤销、发布具有同一裁决顺序 |
| 开放先完成→故障→已取得正文的旧 HTTP/WS 写恢复 | 停止新认证和后续应用层世界提交；不能借 flush 把失效缓冲刷出 | 跨协议发送屏障、部分写入与阻塞写退出；不是只检查整站状态 |
| 旧整文件写已开始→请求取消或超时→新开通请求→旧写晚到 | 旧写仍计账并处理真实效果；未终结前不让新提交与其回盖撤销、运行标记或恢复要求 | 唯一实际写者、串行当前基线、未知效果处理及有界退出 |
| 整站完全停止→同进程重新启动→旧检查成功 | 新运行仍需本次明确开通，旧结果不能匹配；旧写者不因路径相同就获得新运行权限 | 不重用的运行/请求归属，以及旧任务写入和发送能力已消除 |
| 旧文件显示收束→首次读写无痕失败→进程中断后重启 | Q154 阻止自动开放，但人工动作仍不证明没有故障或旧凭证可信 | 首次故障恢复义务跨运行延续；本节不关闭该缺口 |

### 计账与剩余证明

被取消但仍持有 I/O、缓冲或回调的所有者继续计账；不能用重复开通补建任务、释放仍承诺的终态名额，或让 tick 等旧写者退出。普通开通无法准入不等于 Q146 的必要安全更新失败；已校验必要安全更新无法承接时，仍走其既定全站关闭、报告未完成而游戏继续的出口。8/4/3/1 分配、实际内存与有限 I/O 能力均未因此确认。

本节只明确不能发生的转换和候选裁决点。实际同步、持久副作用隔离、全入口迁移、固定平台/硬退出及首次故障留痕仍待证明。[发送屏障专项评估](<observation-send-barrier-engineering.md>)及后续 Q155–Q156 已明确：R 立即拒绝新认证/输出生产，全站最多一个此前获准≤K的写可返回，下一次写前建立匹配 B；只有 B 回执后才可开始该安全状态可靠保存。不能把后来 B 倒推成 R 时已经零输出，也不能把它当持久收束/真实退出证据。Q157 只关闭 PUBLIC 份额选择，未新增超时/重试数、开通意愿有效期、自动恢复路径或额外可信存储；六个相容纸面场景不关闭工程门。
