K 与固定平台依据

先问“证据支持哪个断言”，再问“是否可以放行”。

三个记号，一条条件性结论

  • K：一次通道写调用所见的所有缓冲区 remaining() 总上限，包含 HTTP／WebSocket 协议头。
  • R：已校验限制直接发布，立即拒绝相关新认证和新输出生产。
  • B：输出所有者处理匹配限制，撤销相关后续写资格、丢应用后缀并回执。

检查通过 → R → 全站唯一一次此前获准的写（总输入 ≤ K）→ 返回 → B
此后受影响项不再写；其他仍有资格的输出才可继续。

上述包络须同时有：全入口唯一输出所有权、限制状态可见、一次检查只批准一次写、返回后先处理限制，以及固定实现没有隐蔽后台提交。[项目推导]

K 限制什么K 不限制什么
一次调用暴露的总待写字节；在上述前提下，R→B 的新增残余提交至多 K。整条消息大小、保留内存、调用完成毫秒数、R 前已交 OS 的字节，以及浏览器接收或应用结果。

正常返回 n：0 ≤ n ≤ 本次输入总量，只推进 n；可能为 0。异常没有可用的正常 n，本项目按本次 [0,K] 未知提交、不重放。B 不是保存或真实退出证明。[正常返回契约] [项目异常与保存政策]

报告审查的四个问题

  1. 到底在哪里测？确切 JDK 发行者／完整 build／可信构件与指纹，OS／内核／架构，实际 NIO provider、通道模式和相关包装层；不要只有“Java 21”。
  2. 依赖哪个行为保证？输入及返回、后台提交和关闭契约如何对应这一实现？“非阻塞”不自动承诺硬毫秒上界。
  3. 谁证明产品结构？HTTP、升级、数据／控制帧、旧任务等全入口无旁路，限制发布和逐次检查顺序成立；独立夹具不替代产品证明。
  4. 实测覆盖什么？明确负载与用例下的 CPU、吞吐、延迟、零写／部分写、R/B 轨迹和实际退出；报告未执行项，不能把有限测量外推为所有情况保证。
